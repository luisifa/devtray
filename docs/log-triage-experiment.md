# 日志分诊实验：确定性压缩 vs 原始日志

2026-11-07。目的：判断「便宜模型只读 `devtray logs --digest` 的输出」是否够用，以及确定性压缩到底丢了什么。

## 方法

- **样本**：本机 6 个真实服务日志，不构造数据。
- **两个臂，同一个模型**（`deepseek-flash`），同一提示词与输出 schema：
  - `raw`：日志最后 200 行原文；
  - `digest`：`devtray logs <目标> --digest` 的输出。
- **评分**（每项 0/1）：P1 失败类型正确；P2 定位正确（端点／模块／原因）；P3 下一步动作安全、不误伤。
- **控制组**：样本 2/3/4/5 不是代码缺陷（重启、关机、Ctrl-C、只有警告），用来检测模型会不会编造原因。

输出 schema：

```json
{"failure": true, "class": "no_failure|dependency_unavailable|db_error|data_validation|build_error|interrupted|unknown|other",
 "where": "模块/端点或 null", "cause": "≤40 字", "next_action": "≤40 字",
 "confidence": 0.0, "needs_raw_log": true}
```

## 结果

| # | 服务 | 真实原因 | raw | digest v1 | digest v2 |
|---|---|---|---|---|---|
| 1 | hb_ecom/backend | 登录写入值超过 `varchar(26)` | 3/3 | 2/3 | 3/3 |
| 2 | hb_ecom/web | 系统重启中断 | 3/3 | 1/3 | 3/3 |
| 3 | hb_scf/backend | 关机导致 DB 连接断 | 3/3 | 1/3 | 3/3 |
| 4 | hb_scf/frontend | Ctrl-C 手动停止 | 3/3 | 1/3 | 3/3 |
| 5 | simple-oa/backend | 只有编译警告，仍在启动 | 3/3 | 3/3 | 3/3 |
| 6 | simple-oa/frontend | 后端 3060 未启动 | 3/3 | 3/3 | 3/3 |
| | **合计** | | **18/18** | **11/18** | **18/18** |

输入体积（v2）：

| 服务 | 原始 200 行 | digest | 压缩比 |
|---|---|---|---|
| hb_scf/backend | 31,364 B | 202 B | 155× |
| hb_ecom/backend | 10,969 B | 231 B | 47× |
| simple-oa/frontend | 1,608 B | 143 B | 11× |
| simple-oa/backend | 6,406 B | 683 B | 9× |
| hb_scf/frontend | 1,365 B | 214 B | 6× |
| hb_ecom/web | 272 B | 202 B | 1.3× |

## 发现

1. **模型没有编造。** 6 样本 × 2 臂，没有一次虚构原因；v1 证据不足时会主动降级成 `unknown` + `needs_raw_log`（样本 2 置信度 0.25，样本 4 是 0.7）。控制组的区分能力正常。

2. **v1 掉分全部来自压缩丢信息，不是模型能力。** 三个样本的 raw 臂都能判出「这不是 bug，是机器重启／手动停止」，digest 只能说「不知道」：
   - 关机／重启广播（`The system will reboot now!`）；
   - `^C` 前缀被 ELIFECYCLE 规则吃掉了；
   - 请求端点 `path=/api/auth/login` 被留在被丢掉的那半行里。

3. **补三条确定性规则后，v2 追平 raw，输入仍小 6–155 倍。** 规则分别是：保留一行运行结束上下文、保留 `^C` 的原行、把请求端点提进问题条目。

4. **压缩比取决于噪音量。** 日志本身只有 9 行时（样本 2）几乎没有可压缩空间——那时省 token 的意义本来就小，模型看原文也不会更差。

## 结论

- **先修压缩，再谈模型。** 这次三个失败样本，补三条正则当天解决，零 token、零延迟、零故障点。如果一开始就用模型去补，只会把一个能用规则说清的问题拖进概率世界。
- **便宜模型当「读日志的人」是够用的**：不编造、动作安全、会自我降级。适合放在「贵模型发指令、便宜模型读结果」的位置。
- **现在不做 `devtray diagnose`。** digest 已经给出类型 + 定位 + 次数，模型的主要增量是措辞；真正需要模型的是「跨文件读代码定位根因」，那是 agent 本身的活，不是日志分诊的活。
- 如果以后要做，契约应该是：输入 digest，输出 ≤120 token 的 `cause` / `next_action`，并保留 `needs_raw_log` 逃生口，禁止直接产生写操作。

## 局限

- 6 个样本、每臂只跑一次，没有统计显著性；结论是方向性的，不是精度声明。
- 评分由写这套规则的人完成，存在自评偏差。缓解办法是把评分拆成可核对的事实（类型、端点、原因），而不是「感觉对不对」。
- 只测了一个模型（`deepseek-flash`）。raw 臂让子代理自己读文件，多了一次工具往返，延迟对比因此不可比，故未列入。
- 日志的真实噪音量差异很大，压缩比（1.3×–155×）不能用单一数字概括。

## 复现

```bash
devtray logs <目标> -n 200 > raw.txt
devtray logs <目标> --digest > digest.txt
# 两臂使用同一提示词与 schema，分别喂给同一个模型，按 P1/P2/P3 打分
```
